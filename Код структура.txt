YEBOYBot — карта коду та архітектури
===================================
Гілка розробки: feature/core-v2
Оновлено: 27.10.2026

Це навігація реальними файлами репозиторію. Дерево скорочене: службові
__init__.py, решту legacy helpers та список усіх тестів згорнуто для читабельності.
Шляхи наведено від кореня YEBOYBot; папка може бути на будь-якому диску.
Точні результати перевірок і відомі обмеження: docs/CORE_V2_STATUS_UA.md.

1. З ЧОГО ПОЧИНАТИ
-------------------
Основний Windows-вхід — YEBOYBot.cmd: подвійний клік відкриває українське меню.
Без перевіреного середовища спочатку відкривається PowerShell-панель, яка
працює без Python. Її [1] дозволяє встановити Python 3.12 x64 через офіційний
WinGet для поточного користувача, підготувати .venv-v2 та перевірити бібліотеки.
Потім відкривається головне меню. Наявне справне середовище одразу відкриває
це меню; [24] повертає панель встановлення. Потрібен інтернет/App Installer.
Якщо WinGet відсутній, доступні офіційні посилання, без неперевіреного EXE.

Потік керування:
  YEBOYBot.cmd
    -> tools/windows_setup.ps1        панель до Python, consent і пошук runtime
    -> tools/launcher/bootstrap.py    ізольоване середовище, pip та бібліотеки
    -> tools/launcher/__main__.py     меню та виклик операцій
    -> tools/launcher/process.py      керування процесом і перевірка стану
    -> core_v2/managed.py              lock, heartbeat, контроль завершення
    -> core_v2/bot.py                  Discord-клієнт, команди, фонові задачі

Під час Windows [24] або [5] Python-меню спочатку завершується й передає
керування PowerShell. Бібліотеки замінюються після звільнення .pyd, потім меню
відкривається заново в тому самому CMD. install_v2.bat лишається службовим
Ensure/Repair-входом з уже наявним Python; сам системний Python не встановлює.

Окремий старий режим: [22] у меню або run.bat -> tools/legacy_launcher.py
-> run.py -> yeboybot/bot.py. Його пакети встановлюються лише в .venv-legacy.
Нові функції розвиваються у Core V2; старі cogs збережено для сумісності.

3. МЕЖІ АРХІТЕКТУРИ ТА СТАН МОДУЛІВ
------------------------------------
Новий moderation flow:
  commands.py -> moderation.py -> db.py / discord_moderation.py

Команда формує вхідні дані й приватну відповідь; сервіс перевіряє use-case;
репозиторні операції ізолюють дані через guild_id; adapter виконує Discord REST.
Перед небезпечною дією claim справи має бути збережений у БД. Невідомий API
результат залишається pending; сліпого автоматичного повтору немає. Discord
і SQL не мають спільної транзакції, exactly-once для API не гарантується.
Цей flow використовують /kick, /ban і /unban; /modhistory читає справи сервера.
Ban зберігає повідомлення. Unban працює за ID колишнього учасника й перевіряє
запис блокування. Нові сценарії: core_v2/tests/test_ban_service.py,
test_ban_gateway.py, test_ban_commands.py і test_ban_integration.py у тій самій
папці tests/. Інтеграційні перевірки використовують SQLite та справжні SDK
моделі з підміненою HTTP-відповіддю, без входу до живого Discord.
Окремий flow /clear: commands.py -> clear_commands.py -> clear_service.py
-> clear_repository.py / discord_clear.py. Підтвердження діє 60 секунд для
автора/каналу/сервера; максимум 25 переглянутих повідомлень. До API зберігаються
саме схвалені ID, а /clear-status читає власний request receipt. Clear-запити
мають states clear_* у v2_jobs і не стають фоновими pending-нагадуваннями.
Unknown не повторюється після restart; старі ephemeral-кнопки не відновлюються.
Опис обмежень і перевірок: docs/CLEAR_UA.md.

Створення /warn: commands.py -> ModerationService.warn у moderation.py
-> DiscordGateway.load (fresh guild/owner/roles/actor/bot/target)
-> Database.record_warning у db.py (одна транзакція warn/applied).
Moderate Members автора/бота та ієрархія — політика локального попередження.
Discord mutation/DM/Audit Log запис не викликається. Детермінований guild+interaction
ID та immutable payload блокують повторний запис; revoked і часові мітки
зберігаються. DB outcome після помилки COMMIT може бути unconfirmed, тому
нова ручна команда з новим interaction ID не є безпечним сліпим повтором.
Старі UUID-записи сумісні; нової схеми або міграції немає.
warning_embeds у discord_moderation.py обмежує приватний /warnings список
до 10 записів, екранує причини й рахує UTF-16; повний текст лишається в БД.
Читання /warnings, /unwarn та старі timeout/untimeout ще потребують свіжої
авторизації/lifecycle. Не плутати це зі завершеним створенням /warn.
Нові сценарії: core_v2/tests/test_warn_repository.py, test_warn_service.py,
test_warn_commands.py і test_warn_integration.py у тій самій папці tests/.

У Core уже підключено текстовий XP, рейтинги й durable-нагадування. Нагадування
мають at-least-once delivery: після збою повтор повідомлення можливий.
Таблиці/поля automod, welcome, autorole, voice XP і role panels не означають,
що відповідні Discord-сценарії вже активні. Нові сервіси додаються послідовно.
Повна модерація, подієвий аудит, /setup, /help та webpanel ще не завершені.
Список актуальних slash-команд і межі функцій: docs/MODERATION_UA.md,
docs/CORE_V2_QUICKSTART_UA.md та docs/PROJECT_AUDIT_UA.md.

Core використовує schema2: v2_schema, v2_settings, v2_xp, v2_cases, v2_jobs,
v2_role_panels. Наявна schema1 потребує явної перевіреної міграції з backup;
Discord login автоматично її не застосовує. Для PostgreSQL підтримано лише
стандартну public Core-схему; recovery відновлює власну копію в окрему порожню БД.

4. ЛОКАЛЬНІ ФАЙЛИ: ДАНІ ТА СЕКРЕТИ
-----------------------------------
Це робочі шляхи, а не частина еталонного дерева вихідного коду:
  .env.v2                Токен, URL БД та локальні Core-налаштування
  .venv-v2/              Окреме середовище Core
  .venv-legacy/          Окреме середовище legacy; не змішувати пакети між venv
  data/v2/               SQLite за замовчуванням, lock/state files, reports і logs
  backups/               Перевірені snapshots/маніфести та приватні дані серверів
  config/options.ini     Локальний legacy-токен і налаштування
  config/permissions.ini Локальні legacy-дозволи
  logs/                  Історичні та локальні legacy-журнали

DATABASE_URL може вказувати інший файл SQLite або PostgreSQL; data/v2/yeboy.db
є лише типовим локальним шляхом. Копії даних серверів не шифруються й потребують
приватного зберігання. Не публікуйте .env, токени, URL із паролем або журнали.
Не видаляйте папки даних/копій чи невідоме неповне venv під час очищення коду.

У Git історично відстежуються деякі pyc, logs і JSON-черги. Це не зразок для
нових runtime-файлів; їх виведення з tracking потребує збереження локальних даних.
Карта не містить вмісту таких файлів. У репозиторії немає еталонного Bin/ із
FFmpeg: переносність старого music потребує окремого виправлення шляхів і TLS.

Тести лежать у core_v2/tests/. Вони перевіряють SQL/міграції, process lifecycle,
bootstrap, backup/recovery, permissions, Discord adapters і slash binding.
Unit-тести не повинні входити в реальний Discord; SQL integration потребує
окремої disposable БД. CI-успіх не замінює ручний Windows 10/11, живий Discord
або перевірену експлуатацію 24/7. Старі тестові totals не переносити на новий HEAD.
