# Core v2: запуск і перевірка

Це нове ізольоване ядро у гілці `feature/core-v2`, рання alpha.
На Windows запускайте через `YEBOYBot.cmd`; на Linux — через `python -m core_v2`.
Старий запуск не є точкою входу Core V2.
Для старих команд є [22] головного меню або `run.bat`, окреме `.venv-legacy`;
музика вимкнена за замовчуванням. [Інструкція](LEGACY_LAUNCHER_UA.md).
Поки що це не повна заміна старого бота й не підтверджена готовність до тисяч серверів.

## Windows 10/11

1. На Windows 10/11 x64 завантажте ZIP гілки: https://github.com/VolshebniKGG/YEBOYBot/archive/refs/heads/feature/core-v2.zip
2. Розпакуйте **весь архів** у доступну для запису папку й двічі натисніть `YEBOYBot.cmd`.
   Стартова панель працює через вбудований Windows PowerShell 5.1 ще до появи Python.
3. Виберіть **[1] Встановити все для Core V2 / відновити бібліотеки**.
   Вибір дозволяє встановити відсутній Python 3.12 x64 для поточного користувача
   через офіційний каталог WinGet з погодженням умов пакета й каталогу. Потім
   створюється `.venv-v2`, встановлюються й перевіряються бібліотеки. Потрібен інтернет.
   Якщо WinGet відсутній, використайте офіційні посилання App Installer/Python,
   які покаже панель, і повторно відкрийте CMD. Наявна справна копія одразу
   відкриває головне меню; панель встановлення можна повернути через **[24]**.
4. Після успішної перевірки виберіть **[12]**, введіть токен приховано та ID тестового сервера.
5. Запросіть бота на тестовий сервер зі scopes `bot` і `applications.commands`.
   Права: View Channels, Send Messages, Embed Links, Moderate Members; для `/kick` —
   Kick Members, для `/ban` і `/unban` — Ban Members. Для `/clear` авторові й
   боту потрібні Manage Messages, View Channel і Read Message History у каналі.
   Роль бота має бути вище ролей учасників, яких він модерує.
   Administrator не потрібний. Message Content Intent і Presence Intent не потрібні.
6. Зупиніть старий процес, якщо він використовує той самий токен.
7. У `YEBOYBot.cmd` виберіть [1]. Дочекайтеся готовності й перевірте `/status`.
8. Зупинка через меню: [3]; [2] — перезапуск. [0] залишає бот працювати. Після налаштування команд встановіть `SYNC_COMMANDS=none`,
   щоб не синхронізувати їх на кожному запуску.

[Повне встановлення на чистому ПК, повторний запуск і типові відмови](CLEAN_PC_SETUP_UA.md).
Встановлення Core не додає необов'язковий Git, сервер PostgreSQL, FFmpeg чи
пакети legacy; для звичайного запуску зі SQLite вони не потрібні. Старі функції
мають окреме встановлення через **[22]**. Завантаження бібліотек саме собою
не вмикає ще не завершені модулі. Фактичний стан — [аудит проєкту](PROJECT_AUDIT_UA.md).

За бажанням після звичайного встановлення й перевірки запуску виберіть **[15]**.
У підменю **[1]** введіть `УВІМКНУТИ АВТОЗАПУСК`: Планувальник Windows
запускатиме цю копію бота після входу поточного користувача. Пароль і права
адміністратора не потрібні. Це не запускає бота негайно — для поточної сесії
використовуйте **[1]** головного меню. Для вимкнення відкрийте **[15] → [2]**
і введіть `ВИМКНУТИ АВТОЗАПУСК`; буде видалено перевірене завдання цієї копії.
Уже запущений бот продовжує працювати — зупиняйте його головним **[3]**.
Статус автозапуску не підтверджує готовність Discord. Докладніше:
[автозапуск Windows](WINDOWS_CMD_LAUNCHER_UA.md#автозапуск-windows-через-15).

Краще використовувати окремий Discord application для тестів. Синхронізація замінює
команди відповідної області цього application. `global` публікує команди на всі сервери.
Після переходу test → global тестові команди можуть затіняти глобальні:
їх видалення має бути окремою усвідомленою операцією (автоматично не видаляємо).

Токен не публікуйте й не надсилайте у чат. Якщо раніше токен потрапив до репозиторію,
скиньте його в панелі відповідного провайдера; видалення файлу не стирає історію Git.

## Команди

Core V2 реєструє **18 slash-команд**.

| Команда | Призначення |
|---|---|
| /status | Перевірка БД та кількість серверів |
| /levels enabled | Увімкнути/вимкнути текстовий XP; Manage Server |
| /rank member | XP і рівень на поточному сервері |
| /leaderboard page | 10 учасників на сторінку |
| /kick member reason | Вигнати учасника; Kick Members, актуальна ієрархія та audit case |
| /ban user_id reason | Заблокувати за ID без видалення повідомлень; Ban Members |
| /unban user_id reason | Зняти блокування за ID; Ban Members, поточного членства не потрібно |
| /modhistory user_id state page | Приватна історія справ цього сервера, зокрема pending; по 5 на сторінку |
| /clear amount reason | Приватний перегляд до 25 повідомлень і підтвердження на 60 с; Manage Messages/View Channel/Read Message History |
| /clear-status request_id | Прочитати власний receipt очищення в початковому каналі, без повторного видалення |
| /warn member reason | Зберегти попередження; Moderate Members |
| /warnings member | Останні 10 чинних попереджень; Moderate Members |
| /unwarn case_id | Відкликати попередження цього сервера |
| /timeout member minutes reason | Обмеження від 1 хв до 28 днів |
| /untimeout member | Зняти обмеження |
| /remind minutes message | Нагадування в поточному текстовому каналі |
| /reminders | Ваші активні нагадування цього сервера |
| /cancel-reminder reminder_id | Скасувати своє нагадування |

XP: 5 балів за повідомлення не частіше разу на 60 секунд; ботам і вебхукам не нараховується.
Рівень = ціла частина квадратного кореня з (XP / 100) + 1.
Голосовий XP ще не підключений. Автомодерація, welcome, авторолі, музика,
панель сайту і перенесення старих даних — наступні етапи.

Для нових команд після оновлення: **[11]** → тестовий Guild ID → **[2]**;
потрібна синхронізація SYNC_COMMANDS=test. Для `/ban` і `/unban` використовуйте
1–19 ASCII-цифр ID (значення `0 < ID < 2**63`) і обов'язкову причину до 500 символів.
Ban зберігає повідомлення; unban перевіряє наявність блокування. Повторювати
непідтверджену дію навмання не можна: перевірте `/modhistory` і Discord Audit Log.
[Модерація, дозволи й pending](MODERATION_UA.md).

`/clear amount:1..25 reason` працює лише у звичайному текстовому каналі:
причина 1–200 символів без ASCII/C1 керівних символів і сурогатів. Спочатку
приватний preview; видалення починається лише після кнопки підтвердження автора.
Закріплені, системні та старші 7 діб пропускаються без підбору нових повідомлень,
тому вибраних ID може бути менше за amount. Після restart старі кнопки не
відновлюються; `/clear-status` за 32-символьним ID читає власний receipt.
Це не `/modhistory`: receipt зберігається окремим manual job. Після невідомого
результату не створюйте новий clear навмання — він може вибрати старіші ID.
[Очищення: підтвердження, стани й межі](CLEAR_UA.md).

## Дані, журнали та резервування

- SQLite: `data/v2/yeboy.db`, WAL, початкове створення схеми v2; наявна v1 потребує [21].
- Логи: `data/v2/logs/bot.log`, ротація до 5 архівів по 5 MB.
- `.env.v2` не комітиться; змінні середовища мають пріоритет над файлом.
- Блокування `data/v2/bot.lock` забороняє другий v2-процес у цій папці.
  Іншу копію проєкту чи старий бот це не блокує.

На Windows усі операції доступні через `YEBOYBot.cmd`:

- **[7]** створює SQLite-копію через Backup API, перевіряє цілісність і схему та
  записує поруч `v2-*.db.json` з датою UTC, розміром, версією схеми й SHA-256.
  Конфігурація та токен із `.env.v2` до копії не додаються.
- **[8]** відновлює вибрану копію після зупинки бота через **[3]** і введення
  `ВІДНОВИТИ`. Перевіряються фактичні байти підготовленої копії та сумісність схеми;
  перед заміною створюється резервна копія поточної БД.
- **[20]** показує дату, розмір, повну SHA-256 та стан копій. Enter залишає лише
  перегляд. Введіть кількість останніх перевірених копій, які треба залишити
  поза архівом, перегляньте список і введіть `АРХІВУВАТИ` для перенесення старіших
  у `backups/archive/<uuid>/`. Архівні копії доступні для відновлення через **[8]**.

Стара копія без маніфесту позначається `legacy`: дата й початкова SHA-256 невідомі.
Для її відновлення додатково введіть `СТАРА КОПІЯ` перед `ВІДНОВИТИ`; перевірка
SQLite та схеми залишається обов'язковою. Пошкоджений маніфест або невідповідність
SHA-256 позначаються `invalid` і блокують відновлення навіть із цим підтвердженням.

Архівування не запускається автоматично, не видаляє дані й не звільняє місце
на диску. Копії `legacy` та `invalid`, поточна БД й останні N перевірених копій
не включаються до плану перенесення. SHA-256 виявляє зміну байтів відносно
маніфесту, але не підтверджує авторство: заміна обох файлів не захищена підписом.
Копії не шифруються й містять дані серверів; зберігайте пару `.db` + `.db.json` приватно.
Для PostgreSQL є **[23]**: native Core-backup, явна1→2 міграція й restore
в окрему порожню БД. Потрібні pg_dump/pg_restore. [Інструкція](POSTGRES_RECOVERY_UA.md). Докладно:
[Windows CMD](WINDOWS_CMD_LAUNCHER_UA.md#резервування-та-відновлення).

Старі JSON не імпортуються автоматично: глобальні записи без guild_id потребують рішення власника.

## PostgreSQL та масштабування

Для більшого навантаження підготуйте PostgreSQL, створіть окремого користувача і базу:
`DATABASE_URL=postgresql+asyncpg://USER:PASSWORD@HOST:5432/yeboy`.
Спецсимволи в паролі потрібно URL-екранувати. Перемикання URL не переносить дані SQLite.
Схема створюється автоматично, пул — 10 з'єднань + до 10 додаткових на процес.

AutoShardedBot використовує рекомендовану Discord кількість шардів, якщо SHARD_COUNT порожнє.
Ця alpha розрахована на **один процес**, який керує своїми шардами; не запускайте кілька
копій з тим самим токеном. Координації різних процесів/хостів, Redis і моніторингу ще немає.

Нагадування доставляються з lease 120 секунд і повторними спробами (до 5).
Можливий повтор повідомлення, якщо процес упав після Discord send, але до запису в БД:
це доставка at-least-once, не exactly-once. Дані завершених завдань поки не очищуються.
Недоступний канал/учасник або втрата доступу скасовують доставку без публікації в інший канал.
Завдання серверів, які бот залишив, зберігаються до впровадження політики retention.

Не можна обіцяти місткість ПК за кількістю серверів: важливі активність, RAM, CPU,
мережа, дискові затримки та навантажувальні тести. Для масштабного запуску також
потрібно перевірити актуальні вимоги Discord до верифікації та intents.

## Тести

```powershell
.venv-v2\Scripts\python.exe -m pip install -r core_v2\requirements-dev.txt
.venv-v2\Scripts\python.exe -m pip check
.venv-v2\Scripts\python.exe -m ruff check core_v2
.venv-v2\Scripts\python.exe -m pytest core_v2/tests -q
```

GitHub Actions: workflow **Core v2**, Windows/Ubuntu SQLite та Ubuntu PostgreSQL.
PostgreSQL-тести видаляють таблиці лише в тестовій БД з назвою `yeboy_test`;
не використовуйте робочу базу або робочі credentials.
Перевірки не використовують Discord token і не замінюють перевірку в живому Discord.

Ручний сценарій: два тестові сервери, той самий учасник; перевірте незалежний XP,
попередження і /levels. Перезапустіть бот між створенням і доставкою нагадування.
Перевірте заборону timeout власника/рівної ролі; відмову після видалення прав бота.

## Обмежене відновлення застосунку — 25.10.2026
Managed runtime повторює невдалий запуск до трьох разів із паузами 2/5/15 секунд.
Кожний попередній Bot виходить із async context перед наступною спробою;
OS lock утримується весь час. Навмисне завершення не повторюється, запит [3]
перериває backoff максимум за одну секунду. Неправильний токен, privileged intents
та ValueError конфігурації завершують запуск одразу. Traceback проходить через
редактор секретів у журналі. Меню показує стан відновлення за heartbeat.
Локально 42 passed, 1 Windows-only skipped; Ruff успішний. CI перевіряється окремо.
Це відновлення після Python exceptions, не супервізор аварій ОС/kill/segfault.
Зависання не спричиняє примусового завершення. Живе Discord-підключення не перевірене.
Наступний пріоритет: автоматизація початкової конфігурації та діагностика запуску.


## Майстер конфігурації — 25.10.2026

## Локальна діагностика та JSON-звіт — 25.10.2026

[4] перевіряє Python 3.12, установлені пакети та критичні імпорти, конфігурацію
і файлову SQLite. БД відкривається mode=ro: quick_check, версія v1 та потрібні
колонки; перевірка SQL має progress deadline 2 секунди й lock timeout 1 секунду.
Це не повний integrity_check, тест запису або міграція. Відсутня БД не створюється;
вона готується штатним запуском [1]. PostgreSQL отримує unknown, без підключення.
[18] додатково атомарно зберігає data/v2/diagnostics/latest.json, замінюючи попередній
звіт. Токен, URL БД, ID серверів, nonce, шляхи, журнали й тексти винятків
не включаються. Каталог data/ виключено з Git.
Runtime readiness вимагає свіжого heartbeat і стану «Готовий»; прострочений heartbeat
не підтверджує Discord ready. Чинність токена, мережа та Discord API не перевіряються.
Статуси JSON: ok/error/unknown; local_checks_passed=false також для unknown.
За невдалої локальної перевірки CLI повертає 1, але [18] зберігає доступний звіт.
Кожен виклик меню запускає новий Python-процес, тому перевірка читає актуальну .env.v2.
Локально пройшли 3 stdlib тести експорту/збереження попереднього звіту та відсутньої БД;
інші тести перевіряються в CI нового коміту через недоступні локальні залежності.

## P0: контроль процесу та перевірка схеми

Помилка запису heartbeat тепер завершує керований клієнт і обидві його задачі,
записується у журнал та повертає код 1. Автоматичні повтори для ControlFailure
вимкнені: без записуваного стану новий клієнт не запускається. Запит штатної
зупинки перевіряється перед heartbeat; звичайні мережеві retry залишаються
обмеженими, попередній клієнт закривається до нового запуску.

Якщо запуск завершився з такою помилкою: перегляньте [9], перевірте вільне місце,
права запису в data/v2 і тип об'єктів managed.json/managed.tmp. Після усунення
причини виконайте [4], потім [1]. База даних цим виправленням не видаляється.
Зовнішнього супервізора kill/segfault/збоїв ОС ще немає.

Перед WAL/створенням таблиць перевіряється сумісність наявної схеми. Невідома
версія, порожній/неправильний v2_schema, наявні v2-дані без маркера або неповна
v1 схема відхиляються без автоматичного ремонту. Початкове створення SQLite
виконується транзакційно; помилка DDL відкочує всі його таблиці. Налаштування
та XP підтримуваної v1 зберігаються при повторному запуску.

Не редагуйте version вручну для обходу відмови. Використайте сумісний код і
збережіть оригінал перед перевіреним відновленням. Повний ланцюжок версійованих
міграцій залишається окремим наступним етапом; автоматичного downgrade немає.
Ручний Windows 10/11 і живий Discord API цими тестами не підтверджуються.

## Оновлення на схему v2

Для наявної SQLite v1: зупиніть бот **[3]**, відкрийте **[21]**, перевірте
реальний план і введіть `МІГРУВАТИ`. Лаунчер створить перевірену копію v1
перед транзакцією. Потім **[4] → [1]**. Без підтвердження дані не змінюються.
Нова порожня БД створюється зі схемою v2 під час [1]. Версію вручну не редагуйте.
PostgreSQL v1 відхиляється до Discord login. Для стандартної public Core-схеми
є явний upgrade через **[23]** з перевіреним native backup. Відновлення лише
в окрему порожню БД. Нова PostgreSQL v2 підтримується.
Деталі, сумісність старого коду та rollback: [MIGRATIONS_UA.md](MIGRATIONS_UA.md).
