# Спільнота: привітання, автороль і події

Модуль Core V2 підключений під час запуску, але всі три функції вимкнені, доки адміністратор не задасть відповідні налаштування сервера. Після оновлення синхронізуйте slash-команди через CMD-меню та перезапустіть бота.

| Команда | Дія |
|---|---|
| `/community welcome channel:#вітаємо` | Текстове привітання нових учасників |
| `/community autorole role:@Учасник` | Безпечна роль для нових людей після Membership Screening |
| `/community logs channel:#події` | Події входу/виходу, створення/видалення каналів і ролей |

Виклик команди **без каналу або ролі вимикає** відповідну функцію. Налаштування зберігаються окремо для кожного сервера й переживають перезапуск.

Для всіх команд потрібен дозвіл «Керувати сервером», для авторолі також «Керувати ролями». Перевірка відбувається під час виконання; прихованість команди в Discord не замінює перевірку. Боту потрібні View Channel і Send Messages у вибраному каналі; для видачі ролей — Manage Roles. Роль має бути нижчою за ролі бота та автора налаштування (власник сервера звільнений від обмеження власної ієрархії).

Для привітань, авторолей і входів/виходів увімкніть `ENABLE_MEMBERS=true` у `.env.v2` та **Server Members Intent** у Discord Developer Portal. Потім перезапустіть бота. Ролі й канали можуть журналюватися без Members Intent. Кеш нових учасників потрібний, щоб отримати завершення Membership Screening; він збільшує використання пам’яті пропорційно кешованим учасникам. На великих серверах потрібно виміряти витрати.

Автороль не видається ботам, учасникам із незавершеним Screening та тим, хто вже має роль. Керовані інтеграціями, `@everyone`, адміністративні й модераторські ролі відхиляються. Перед кожною видачею повторно перевіряються поточні кешовані права ролі й ієрархія бота. Особа, яка налаштувала автороль, не зберігається в наявній схемі БД; її подальші зміни прав не перевіряються. Після вимкнення Members Intent події не надходитимуть. Після простою бот не відновлює пропущені входи й не роздає ролі всім учасникам заднім числом.

Повідомлення не викликають сповіщень через mentions. Журнал містить тип події та Discord ID, без текстів приватних повідомлень, назв приватних каналів або спроб вгадати виконавця. Це **обмежений журнал подій**, а не повний Discord Audit Log: редагування повідомлень, банів і прав цей модуль не протоколює.

Кожна операція БД/API має таймаут 15 секунд. Одночасно допускається до 16 обробників цього модуля на процес; зайві події відкидаються, щоб не накопичувати необмежену чергу під час рейду. Доставка найкращим зусиллям: без повторів, гарантії збереження або відновлення пропущених подій. Відсутність каналу/прав і помилки API не зупиняють бота. Повідомлення про помилки не містять токенів чи сирих відповідей сервісів.

## Ручна перевірка

1. На окремому тестовому сервері налаштуйте три команди та перевірте вхід нового учасника.
2. Увімкніть Membership Screening: до прийняття правил ролі бути не повинно, після прийняття вона має з’явитися.
3. Перемістіть роль вище бота або додайте їй адміністративні права: новому учаснику вона не повинна видаватися.
4. Заберіть Send Messages у каналі: подальші події не повинні спричиняти аварій.
5. Перезапустіть бота та перевірте збереження конфігурації. Вимкніть функції командами без параметрів.

Автоматичні тести використовують підроблені Discord-об’єкти. Справжні Discord події, токен, Members Intent і поведінку Screening потрібно перевірити наведеним сценарієм.

Під час зупинки модуль припиняє приймати події та зміни налаштувань, дає
активним операціям до двох секунд на завершення, потім скасовує й очікує їх
очищення перед закриттям БД. Доставка вже розпочатого повідомлення не гарантується,
а прийнятий Discord-запит скасування локальної задачі не відкочує.
