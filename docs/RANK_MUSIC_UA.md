# Картка рангу, голосовий XP і музика Core V2

Core V2 використовує `discord.py` та власну SQL-базу. Старі `yeboybot/rank.py`
і `yeboybot/music.py` залишаються в окремому legacy-середовищі й не завантажуються
в Core. Оновлення повертає графічну картку `/rank`, додає облік голосової участі
та добровільно ввімкнений модуль `/music`. Воно не підтверджує роботу з реальним
Discord або безперервність відтворення протягом 24 годин.

## Ранг і активність

Використайте `/rank` для себе або `/rank member` для іншого учасника цього
сервера. Картка — PNG 500×188 на основі наявного `DLC/rank_background.png`;
`DLC/gg.png` задає маски великої комірки аватара та малої комірки іконки сервера.
Шрифт `DLC/font.ttf` підтримує українську. Картка показує незалежні:

- текстовий XP, рівень, місце й прогрес до наступного рівня;
- голосовий XP, рівень, місце й прогрес до наступного рівня.

Для PNG-картки боту потрібні **Attach Files** і **Embed Links** у каналі.

Велика комірка містить аватар вибраного учасника, мала — іконку поточного
сервера. Відсутня або недоступна іконка має нейтральну заміну. Довгі імена
скорочуються; завантаження аватарів і генерація зображення обмежені в часі та
за ресурсами. Помилка БД не підміняється нульовим XP.

Текст: **5 XP**, не частіше одного нарахування на 60 секунд для одного
учасника одного сервера. Боти й вебхуки не отримують XP. Message Content Intent
для підрахунку подій не потрібний; бот не аналізує зміст повідомлень. Це cooldown,
а не семантична перевірка якості розмови.

Голос: **5 XP за повну спостережену хвилину** в одному звичайному голосовому
каналі, де одночасно є щонайменше двоє придатних учасників-людей. Боти,
AFK-канал, Stage, mute/deaf/self-mute/self-deaf/suppress не зараховуються.
Вихід, зміна каналу чи втрата придатного співрозмовника скидає незавершену
хвилину. Після втрати спостереження або перезапуску пропущені хвилини не
наздоганяються. Discord не надає цим кодом підтвердження фактичного мовлення:
враховується доступна голосова присутність, аудіо не прослуховується й не зберігається.

Рівні сумісні з формулою старої картки:

```text
текстовий рівень = floor(sqrt(text_xp / 100)) + 1
голосовий рівень = floor(sqrt(voice_xp / 50)) + 1
```

Нуль XP відповідає рівню1. Прогрес починається від порогу поточного рівня;
наприклад, текстовий рівень2 має межі100–400 XP. Місця обчислюються окремо
в межах сервера; за однакового XP використовується порядок user_id.
`/leaderboard` без вибору типу показує суму текстового й голосового XP;
параметр `xp_type` дозволяє окремо вибрати **Чат** або **Голос**.
`/levels enabled:false` вимикає обидва способи нарахування, не видаляючи XP.
Для зміни потрібен дозвіл «Керувати сервером».

### Окремі рейтинги чату й голосу

| Виклик | Що порівнюється |
|---|---|
| `/leaderboard` | Сума текстового й голосового XP; попередня поведінка збережена |
| `/leaderboard xp_type:Загальний` | Та сама сума чату й голосу |
| `/leaderboard xp_type:Чат` | Лише текстовий XP, відповідно до текстового місця `/rank` |
| `/leaderboard xp_type:Голос` | Лише голосовий XP, відповідно до голосового місця `/rank` |

Параметр `page` збережений: від 1 до 1000, по 10 профілів XP поточного
сервера на сторінку. Нумерація продовжується між сторінками. Порядок — від
більшого вибраного XP до меншого; за однакового значення менший Discord ID
розташований вище. Загальний рейтинг може відрізнятися від обох окремих
місць на картці: він використовує іншу величину, суму двох лічильників.
Порівнюються збережені профілі XP цього сервера, зокрема історичні профілі
учасників, які вийшли. Це не перелік поточного складу Discord, його історія
не видаляється під час перегляду рейтингу.

Для допустимих великих цілих лічильників сума відображається точно, навіть
коли вона перевищує межу одного signed 64-bit числа. Порядок не залежить
від округлення SQLite до float, а PostgreSQL не обчислює переповнену bigint
суму. Це виправлення читання й сортування: XP, рівні, старі налаштування та
власні assets картки не скидаються й не перезаписуються.

Рейтинг доступний учаснику сервера й надсилається публічно. Згадки не
сповіщають користувачів. Порожня сторінка показує «Поки немає XP»;
помилка БД або таймаут не підміняються порожньою успішною відповіддю.
Звіт обмежений 10 профілями; читання БД — 10 секундами. У відповідь про
помилку не потрапляють рядки даних, SQL, шлях БД або credentials. Помилка теж
публічна: після публічного defer видимість першої відповіді не змінюється.

Для нового параметра `xp_type` потрібна синхронізація обраної області
через **`YEBOYBot.cmd` → [11]**, потім **[2] Перезапустити**.
За `SYNC_COMMANDS=none` metadata не публікується. Нових команд верхнього рівня,
залежностей, міграцій чи intents це оновлення не додає.

Потрібний неперевілейований Voice States Intent. Members Intent не потрібний
для обліку голосових учасників; кеш обмежений голосовою присутністю.
Файл `data/rank/<guild_id>/levels.json` старого бота й SQL Core V2 — різні
сховища: відновлення графіки саме собою не переносить старий прогрес.
Старі файли не видаляються й не перезаписуються.

Для явного перенесення в наявну SQLite v2: **[3] зупинити → [26] → ID сервера →
ІМПОРТУВАТИ XP → [1] запустити**. Перед записом перевіряється весь JSON і
створюється перевірена резервна копія. Зупиніть також legacy-бот, якщо він
пише цей JSON. Кожен лічильник стає максимумом старого
й поточного: бали не зменшуються, повторний імпорт не додає їх вдруге.
Збережений у JSON рівень ігнорується й обчислюється з XP. Для PostgreSQL
цей імпорт недоступний; автоматичного обнулення чи перенесення немає.

## Увімкнення музики через Windows-меню

1. Відкрийте оновлений `YEBOYBot.cmd`. На новому ПК виберіть установлення
   Core V2; для наявної копії зупиніть бот через **[3]**, потім **[5]** для
   встановлення нових бібліотек. Вони встановлюються тільки в `.venv-v2`.
2. Відкрийте **[25] Музика: options.ini / FFmpeg / увімкнення**.
3. Якщо FFmpeg відсутній, виберіть підпункт **[3]**. Перед встановленням через
   WinGet введіть запропонований текст підтвердження `ВСТАНОВИТИ FFMPEG`.
   Використовується точний пакет `Gyan.FFmpeg` з каталогу WinGet, штатна перевірка
   пакета й установлення для поточного користувача. Права адміністратора
   автоматично не запитуються, невідомий EXE з Інтернету не запускається.
4. Для YouTube потрібні пакет `yt-dlp-ejs` (установлюється з Core) та
   підтримуваний Deno або Node.js≥20. Якщо runtime відсутній, **[25] → [4]**
   встановлює `DenoLand.Deno` через WinGet лише після `ВСТАНОВИТИ DENO`.
   Наявний runtime використовується без нового встановлення.
5. Поверніться до **[25] → [1]**. Перевіряються музичні бібліотеки та шлях FFmpeg;
   `config/options.ini` створюється з прикладу лише за відсутності, а
   `ENABLE_MUSIC=true` зберігається в `.env.v2`. Наявні параметри не переписуються.
6. У **[11]** налаштуйте тестову синхронізацію команд на потрібний сервер і
   перезапустіть бот через **[2]**. Боту потрібні View Channel, Connect і Speak
   у голосовому каналі. Учасник також має бачити канал, підключатися й говорити.
7. Приєднайтеся до голосового каналу та виконайте `/music play query`.
   Для підключення лише автоплейлиста адміністратор може використати `/music join`.

Для вимкнення: **[25] → [2]**, потім перезапуск. Змінні середовища мають пріоритет
над `.env.v2`: якщо `ENABLE_MUSIC` задається зовнішньою службою, змініть його там.
Токен вводьте приховано через основне меню; не надсилайте конфігурацію в чат.

FFmpeg не додається бінарним файлом до Git-репозиторію. Можна використати власне
довірене встановлення й задати `FFMPEG_PATH` у `.env.v2`; підтримуються шляхи
з пробілами та кирилицею. Пошук також враховує `bin/ffmpeg.exe`, WinGet Links і
PATH. Якщо WinGet недоступний, установіть офіційний App Installer за посиланням
у меню або підготуйте FFmpeg самостійно. Linux: потрібні FFmpeg і системна `libopus`; установіть їх штатним
пакетним менеджером ОС, установіть залежності Core в `.venv-v2`, задайте
`ENABLE_MUSIC=true`, перевірте конфігурацію та перезапустіть службу.

## Конфігурація options.ini

Змінюйте **`config/options.ini`**, а не відстежуваний `example_options.ini`.
Якщо runtime-файла немає, музичні параметри читаються з прикладу.
Core підтримує такий обмежений набір історичних ключів:

| Розділ / ключ | Поведінка Core V2 |
|---|---|
| Credentials / Token | Резервний Discord-токен, лише якщо `DISCORD_TOKEN` порожній; значення прикладу не є токеном |
| Chat / AutojoinChannels | До20 ID звичайних голосових каналів через пробіл; бот пробує приєднатися після готовності |
| MusicBot / DefaultVolume | Початкова гучність0.01–1.0 |
| MusicBot / UseAutoPlaylist | Початкове ввімкнення `config/_autoplaylist.txt` |
| MusicBot / AutoPlaylistRandom | Випадковий вибір або послідовний обхід списку |
| MusicBot / AutoPlaylistAutoSkip | Чи переривати автотрек, коли з'явилося замовлення |
| MusicBot / AutoPause | Пауза, коли в каналі немає людей; для постійного звучання порожнього каналу — `no` |
| MusicBot / SelfDeafen | Чи підключатися з вимкненим отриманням аудіо |

Приклад для одного сервера:

```ini
[Chat]
AutojoinChannels =

[MusicBot]
DefaultVolume = 0.25
UseAutoPlaylist = yes
AutoPlaylistRandom = yes
AutoPlaylistAutoSkip = yes
AutoPause = yes
SelfDeafen = yes
```

Додайте ID свого голосового каналу після `AutojoinChannels =`, якщо потрібне
підключення після старту. Не використовуйте чужі ID з прикладів. Один сервер
має один голосовий плеєр; кілька ID того самого сервера не створюють кілька
підключень.

Для Spotify track-посилань заповніть власні `Credentials/Spotify_ClientID` і
`Credentials/Spotify_ClientSecret`. Використовується офіційний Spotify API
метаданих через client credentials; відповідний відкритий запис шукається
на YouTube. Секрети не передаються в argv або журнал.

Інші численні ключі історичного прикладу не означають реалізовані функції Core.
Зокрема, префіксні `!`-команди, голосування за skip, permanent audio cache,
historical permissions groups, OAuth bypass і legacy storage-політики не
підключаються читанням цього INI. Команди Core — slash-команди.
`Credentials/Token` не замінює решту `.env.v2`: БД, sync, shard-параметри та
ввімкнення музики лишаються в конфігурації Core.

## Черга, автоплейлист і керування

| Команда | Призначення |
|---|---|
| `/music play query` | Замовити трек за підтримуваним посиланням або назвою |
| `/music join` | Підключити плеєр; «Керувати сервером» |
| `/music queue` | Поточний трек, стан і до10 наступних замовлень |
| `/music skip` | Пропустити власний трек чи автоплейлист; чужий — «Керувати сервером» |
| `/music pause` | Установити ручну паузу наявної сесії; «Керувати сервером» |
| `/music resume` | Зняти ручну паузу наявної сесії; «Керувати сервером» |
| `/music autoplay enabled` | Змінити автоплейлист поточної сесії; «Керувати сервером» |
| `/music stop` | Очистити чергу й від'єднати бота; «Керувати сервером» |

Керування вимагає перебування в тому самому голосовому каналі. Перевіряються
поточне членство й доступ до каналу. Команди відповідають приватно без mentions.
Назви й URL не виконуються як shell-команди.

У кожного сервера окрема FIFO-черга, до50 замовлень. Одночасно дозволено
до20 плеєрів і до2 процесів отримання медіа. Пріоритет мають замовлення:
за `AutoPlaylistAutoSkip=yes` нове замовлення перериває поточний автотрек;
після спорожнення черги бот знову бере трек із `_autoplaylist.txt`.
За `no` замовлення чекає завершення автотреку. Чужі замовлені треки не
перериваються новим замовленням.

У `_autoplaylist.txt` задавайте по одному підтримуваному посиланню/запиту
на рядок. Порожні рядки та коментарі `#`/`;` пропускаються. До10000 рядків,
не більше500 символів на запис; файл не переписується через помилки джерела.
Після зміни файла або INI перезапустіть бот. Невдалі джерела не створюють
щільного restart loop: між спробами діє зростаюча пауза до60 секунд.

`/music stop` забороняє автопідключення цього сервера до нового запиту чи
перезапуску процесу. Черга й перемикач `/music autoplay` зберігаються в пам'яті:
після перезапуску замовлення не відновлюються, а параметри знову читаються з INI.
Для відтворення протягом доби потрібні працюючий процес, доступний сервер,
голосове підключення, джерела й мережа. Це можливість автоматично продовжувати
чергу, а не перевірений SLA24/7.

## Джерела та межі

Підтримуються HTTPS-посилання YouTube/SoundCloud і пошук за назвою на YouTube.
Плеєр отримує відкритий аудіопотік через `yt-dlp`; зберігання повних медіафайлів,
cookies користувача, вимкнення TLS-перевірки й обхід DRM не використовуються.
Один запит означає один трек, не необмежений імпорт плейлиста; live-потоки
й треки довші4 годин відхиляються. Доступність конкретного відео, географічні
обмеження та зміни сайтів можуть завадити відтворенню. Використовуйте матеріали,
для яких маєте відповідний дозвіл і які доступні за правилами джерела.

Посилання Spotify не дає Discord-боту права отримувати повний оригінальний
аудіопотік Spotify. Якщо налаштовано офіційне отримання метаданих треку,
назва й виконавець використовуються для пошуку відповідної версії на YouTube;
це може бути інша версія запису. Spotify playlist/album та пряме відтворення
захищеного Spotify-аудіо не заявляються.

## Перевірка після оновлення

На окремому тестовому сервері перевірте `/rank`, повідомлення з інтервалом
понад60 секунд і розмову двох нем'ютованих учасників у звичайному каналі.
Потім перевірте автотрек → замовлений трек → повернення до автоплейлиста,
вихід людей із каналу, `/music stop` та перезапуск. Вимкнення XP має зберігати
попередні значення. Не використовуйте свій основний сервер для перевірки
непідтверджених сценаріїв.

Автоматичні тести SQL, зображення, черги й підміни Discord/джерел описують
лише перевірені межі. Актуальні кількості, платформи й CI наведені в
[CORE_V2_STATUS_UA.md](CORE_V2_STATUS_UA.md). Реальні голосове підключення,
стримінг джерел, Spotify credentials і тривалий24/7 сценарій перевіряються окремо.

## Діагностика джерел і надійна зупинка — 28.10.2026

`/music queue` показує український стан плеєра та останню відому категорію
помилки. Класифікація спирається на доступні ознаки відповіді джерела;
вона допомагає перевірці, але сама собою не доводить причину мережевого збою.

| Категорія | Що перевірити |
|---|---|
| Мережа | Інтернет, DNS, налаштований proxy; повторити пізніше |
| TLS | Системний час і довірені сертифікати; перевірку TLS залишити ввімкненою |
| Обмеження запитів | Зачекати або вибрати інший трек; backoff лишається активним |
| Потрібен вхід | Вибрати відкритий трек; бот не входить в облікові записи джерела |
| Формат недоступний | Перевірити інше джерело або після зупинки оновити бібліотеки через [5] |
| JS runtime | Перевірити Deno/Node.js≥20; установлення Deno через [25]→[4] |
| Таймаут | Спробувати інший трек або повторити пізніше |
| Відтворення | Перевірити FFmpeg, voice-бібліотеки й дозволи каналу |

Сирі stderr, URL із підписами, query та credentials не виводяться. Extractor
передає тільки код із дозволеного переліку; невідомий код має загальну безпечну
підказку. Ввід worker обмежений16KiB, stdout64KB, читання потокове. Перевищення
ліміту, timeout і cancellation запускають обмежене завершення власного Python
процесу та дренування його pipes; інші процеси Python не завершуються.
Окрему гарантію завершення Deno-нащадків на всіх ОС ще потрібно перевірити.

`/music stop` тепер блокує також автопідключення, яке очікувало REST-відповіді
або голосового handshake. Пізно отримане власне з'єднання закривається перед
публікацією сесії. Нова явна команда play/join може запустити музику знову.
Неправильне посилання відхиляється до створення голосового з'єднання.

Скасування команди під час від'єднання не кидає власний teardown: він лишається
під контролем до завершення, а повторне підключення цього сервера чекає його
закінчення. Незалежні сервери від'єднуються паралельно. При видаленні бота із
сервера старий запит не може опублікувати нову сесію.

У попередній ітерації діагностики нових slash-команд чи налаштувань не додавали.
Щоб застосувати саме ті зміни, оновіть код гілки feature/core-v2 через головне
меню й перезапустіть бот через [2].
Синхронізація команд і повторне встановлення системних компонентів для цих
змін не потрібні. Live Discord і тривалий24/7 тест лишаються окремою перевіркою.

## Непідтверджена зупинка та повторна спроба

`/music stop` повідомляє про успіх лише після завершення плеєра, очищення
аудіопотоку й підтвердженого локального від'єднання голосового клієнта. Помилка або
таймаут цих операцій не означають, що з'єднання вже закрито.

Перевірка охоплює завершення обмеженого виклику SDK без спливання його дедлайну,
`voice.is_connected() == False` та результат очищення аудіо. Це підтвердження
локального стану discord.py, а не незалежне підтвердження voice-state від
сервера Discord: SDK може приховати частину транспортних помилок. Воно також
не доводить завершення всіх native-ресурсів після зависання.

За непідтвердженого результату бот зберігає власну сесію, блокує для неї
нові треки й підключення та показує стан у `/music queue` і `/modules`.
Він не створює другий voice-клієнт, щоб обійти збій. Власний клієнт береться
під облік під час створення, до очікування handshake; це охоплює також
пізно завершене підключення, яке вже було скасовано командою зупинки.
Скасування Discord-команди не скасовує окреме контрольоване завершення сесії.
Сервери можуть завершувати свої сесії незалежно.

1. Залишайтеся в тому самому голосовому каналі. З дозволом «Керувати сервером»
   повторіть `/music stop`: це ще одна обмежена спроба закриття тієї самої
   сесії, а не нове підключення. Одночасні команди використовують одну спробу.
   Дозволи учасника й голосовий канал перевіряються; втрата ботом Connect/Speak
   не повинна блокувати закриття вже створеної сесії.
2. Перевірте відповідь. За успіху можна виконати `/music play` або `/music join`.
   За повторного непідтвердженого результату не вважайте сесію закритою.
3. Зверніться до власника бота: перегляньте журнал і виконайте штатний
   перезапуск через **`YEBOYBot.cmd` → [2]**. Черги зберігаються лише в пам'яті
   й не відновлюються після перезапуску. Не завершуйте сторонні процеси Python.

Нескінченного автоматичного повторення від'єднання немає. Якщо cleanup
FFmpeg завершився помилкою, його успіх не підміняється прапорцем завершення;
повтор `/music stop` не гарантує відновлення такого native-процесу.
Фактичне закриття всіх native-ресурсів після зависання потребує окремої
перевірки на Windows і з реальним Discord.

Для миттєвого завершення треку діє backoff навіть після довгого пошуку джерела:
відлік починається перед передачею треку плеєру, після отримання медіаданих.
Це час роботи планувальника до callback з урахуванням очищення, а не
вимірювання реально почутого аудіо. Нормальне завершення скидає лічильник
помилок; пропуск і переривання автотреку замовленням не вважаються збоєм.

Для попереднього оновлення контролю завершення сесій не потрібні нові
залежності, міграція БД, intents чи синхронізація команд. На тому етапі було 20 основних
команд і 6 підкоманд `/music`. Поточний модуль має 20 основних команд і 8
підкоманд `/music`; для нових pause/resume потрібна sync, описана нижче.
Автоматичні перевірки й CI поточного коміту наведено у
[статусі](CORE_V2_STATUS_UA.md) та [PR#1](https://github.com/VolshebniKGG/YEBOYBot/pull/1).
Live Discord, ручний чистий Windows і тривалий 24/7 тест не підтверджені.

## Ручна пауза й відновлення

`/music pause` установлює ручну паузу поточної музичної сесії, а
`/music resume` знімає її. Потрібні дозвіл **«Керувати сервером»** і
перебування в поточному голосовому каналі бота. Ці команди не підключають
бота й не створюють сесію: спочатку використайте `/music play` або `/music join`.

Ручна й автоматична паузи незалежні:

| Ситуація | Результат |
|---|---|
| Установлено ручну паузу, людина приходить у канал | Ручна пауза залишається |
| Установлено ручну паузу й спрацьовує AutoPause | Обидві причини паузи зберігаються |
| Виконано resume, але AutoPause порожнього каналу ще активна | Ручну паузу знято; автоматична продовжує утримувати аудіо |
| Пропущено трек або додано замовлення під час ручної паузи | Ручна пауза діє й для наступного треку; замовлення не обходить її |
| Сесію зупинено або бот перезапущений | Ручна пауза не відновлюється з БД чи INI |

Пауза може бути встановлена під час отримання треку або очікування замовлень.
До відновлення плеєр не споживає наступне замовлення чи запис автоплейлиста
й не починає нове отримання джерела. Уже розпочате отримання завершується
зі звичайним таймаутом. Якщо воно успішне, запит чекає відновлення й повторного
отримання свіжого аудіопосилання: підписаний URL не є безстроково придатним.
Помилка джерела обробляється як звичайний збій треку з паузою між спробами;
ручна пауза не перетворює такий запит на гарантовано збережене замовлення.

Прапорець ручної паузи діє лише в пам'яті цієї сесії. Це не збережена
конфігурація сервера й не гарантія того, що слухач почув або не почув аудіо.
`/music queue` розрізняє ручну й автоматичну причини та доступний локальний
стан паузи SDK; невідомий стан не підміняється підтвердженим відтворенням.

Під час втрати голосового з'єднання pause/resume відхиляються з підказкою
повторити після відновлення. Намір ручної паузи зберігається. Для сесії,
що завершується або має непідтверджене очищення, дії відтворення заблоковані:
використайте [повтор зупинки](#непідтверджена-зупинка-та-повторна-спроба).

Щоб нові підкоманди з'явилися в Discord:

1. Оновіть код `feature/core-v2` й відкрийте `YEBOYBot.cmd`.
2. Через **[11]** перевірте синхронізацію в обраній області. Для тестового
   сервера збережіть його ID; режим `SYNC_COMMANDS=none` команди не публікує.
   Глобальну публікацію не потрібно вмикати заради тестового сервера.
3. Перезапустіть через **[2]**, дочекайтеся готовності, перевірте `/help` → Музика
   та `/music pause` / `/music resume` у наявній сесії.

Додаткові бібліотеки, міграції, intents і системні компоненти для паузи не
потрібні. Основних команд залишається 20, у групі `/music` тепер 8 підкоманд.
Живий Discord, ручний Windows і тривалий тест відтворення лишаються окремими
перевірками; результати автоматичних тестів дивіться за поточним SHA.
