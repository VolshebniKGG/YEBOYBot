# Модерація Core V2: дії, підтверджене очищення та історія

У Core V2 зареєстровано **18 slash-команд**, зокрема `/kick`, `/ban`, `/unban`,
`/modhistory`, `/clear` і `/clear-status`. Старі prefix-команди legacy — окрема
реалізація, а не підтвердження готовності відповідних slash-команд.

## Увімкнення команд на тестовому сервері

1. Відкрийте **YEBOYBot.cmd → [11]**, задайте ID окремого тестового сервера.
   Майстер збереже `TEST_GUILD_ID` і `SYNC_COMMANDS=test`; наявний токен можна
   залишити без зміни прихованим порожнім введенням.
2. Переконайтеся, що application запрошений зі scopes `bot` і `applications.commands`.
3. Виконайте **[2] Перезапустити бота** та дочекайтеся підтвердженої готовності.
   Команди синхронізуються з тестовим сервером. `global` не потрібний для перевірки.
4. Після успішної реєстрації за бажанням змініть `SYNC_COMMANDS=none` у `.env.v2`
   і перезапустіть бот, щоб не синхронізувати команди при кожному старті.
   Змінні середовища мають пріоритет над файлом. Синхронізація test/global може
   замінювати команди відповідної області application; автоматично старі області
   не очищуються.

Не публікуйте токен, `.env.v2` чи скриншот його вмісту. Для цих команд не
потрібно вмикати Message Content або Members Intent: актуальні окремі учасники
читаються через REST. Це не замінює ручну перевірку дозволів у вашому Discord.

## /kick member reason

Авторові та боту потрібен **Kick Members / «Виганяти учасників»**; Administrator
також враховується. Роль учасника має бути нижчою за ролі автора і бота.
Власник сервера обходить обмеження власної ієрархії, але роль бота все одно
повинна бути вищою за роль цілі. Себе, цього бота й власника вигнати не можна.

Причина обов'язкова: 1–500 символів, порожній після видалення крайніх пробілів
текст відхиляється. Повна нормалізована причина зберігається в БД.
У Discord Audit Log передається `case=<ID>; actor=<ID>; ...`; довга причина
скорочується до межі 512 URL-encoded символів зі збереженням префікса справи.

Перед дією бот заново отримує сервер, owner ID, ролі, автора й самого себе.
Після запису справи він повторює перевірку з ціллю безпосередньо перед DELETE.
Невідомі role IDs відхиляються; спільний Gateway-кеш не підміняється.
Зміна ролей між перевіркою й запитом Discord усе ще можлива: ці операції
не є атомарними. Остаточний результат залежить від Discord API.

Відповідь містить ID справи та підтверджений стан, якщо він відомий, і доступна
лише автору команди. Mentions вимкнені. Невдала доставка відповіді не означає, що kick не відбувся:
перевірте `/modhistory`, а не повторюйте команду навмання.

## /ban user_id reason

Авторові та боту потрібен **Ban Members / «Блокувати учасників»**; Administrator
також враховується. Команда приймає числовий ID: 1–19 ASCII-цифр, значення
більше нуля й менше `2**63`. Для копіювання ID увімкніть у Discord режим
розробника й виберіть «Копіювати ID користувача» в меню людини.
Не вводьте згадку `<@...>` або display name замість ID.

Якщо користувач зараз на сервері, бот отримує його актуальні ролі через REST:
ціль має бути нижчою за автора й бота. Власник обходить власну ієрархію,
але не ієрархію бота; Administrator не обходить перевірку ролей автора.
Якщо Discord точно повернув `404 / Unknown Member (10007)` для цілі,
можна заблокувати користувача поза сервером. Йому не вигадуються ролі:
порівнювати поточну ієрархію відсутнього учасника немає з чим. Інша 404,
відмова доступу, збій мережі або відсутність автора/бота блокують дію.
Себе, цього бота й актуального власника сервера заблокувати не можна.

**Повідомлення зберігаються:** adapter явно надсилає
`delete_message_seconds=0`. Параметра видалення історії в цій команді немає.
Це важливо, оскільки стандартна поведінка SDK без цього аргументу інша.
Причина обов'язкова, 1–500 символів після обрізання крайніх пробілів;
NUL відхиляється. Повна причина зберігається в БД, audit-header обмежується
так само, як у `/kick`. Якщо ID уже заблокований, підтвердження запиту Discord
не доводить, що саме ця команда вперше змінила його стан.

## /unban user_id reason

Авторові та боту потрібен **Ban Members / «Блокувати учасників»**.
Формат ID і причини такий самий, як у `/ban`. Поточного членства користувача
на сервері не потрібно: команда працює з записом блокування за ID.
Себе, цього бота й актуального власника як ціль відхиляють обидві команди.

Після запису справи бот повторно отримує актуальні права автора/бота й
перевіряє блокування через Discord. Лише точна відповідь
`404 / Unknown Ban (10026)` означає, що запису немає: unban не надсилається,
а справа за успішного запису результату отримує `failed` із поясненням.
Інші помилки читання не вважаються доказом відсутності блокування; вони теж
зупиняють дію до unban. Ієрархія ролей відсутнього учасника не перевіряється
й не вигадується; дозволи автора/бота та власник перевіряються заново.

Між читанням блокування й запитом його може змінити інший модератор.
Після надсилання unban помилка, включно з 404, залишає результат
непідтвердженим: не можна видавати її за доказ невиконаної дії.

## /modhistory user_id state page

Усі параметри необов'язкові. `user_id` — числовий ID, зокрема колишнього
учасника; присутність цієї людини на сервері для читання історії не потрібна.
ID має містити 1–19 ASCII-цифр і вкладатися в додатний signed BIGINT.
`page` — від 1 до 1000, по **5 справ**; порядок стабільний за часом створення
та ID від нових до старих. Без фільтрів показуються справи поточного сервера.

| Вибір state | Збережений стан | Значення |
|---|---|---|
| Непідтверджено | `pending` | Результат не підтверджений; потрібна перевірка |
| Застосовано | `applied` | Результат зафіксовано як застосований |
| Зафіксовано помилку | `failed` | У справі записано помилку; фактичний результат старих API-дій потрібно перевірити |
| Відкликано | `revoked` | Попередження відкликане |

Історію може читати власник або учасник з актуальним Kick Members, Ban Members,
Moderate Members чи Administrator. За замовчуванням Discord показує команду
користувачам із **Moderate Members**. Якщо роль має лише Kick Members або
Ban Members, налаштуйте доступ до `/modhistory` у Discord **Server Settings →
Integrations → application → Commands**. Це налаштування видимості не обходить
перевірку актуальних прав під час виконання.

Відповіді приватні для автора, текст причин екранується, mentions вимкнені.
Історія читає тільки `guild_id` поточного сервера, не змінює записи й не
виконує повторних модераційних дій. Для читання власної БД боту не потрібен
View Audit Log; цей дозвіл потрібен людині для ручної звірки журналу Discord.

## /clear amount reason та /clear-status request_id

`/clear` читає одну сторінку до 25 останніх повідомлень перед командою у
звичайному текстовому каналі. Закріплені, системні та старші за 7 діб
пропускаються без підбору замін. Кількість фактично вибраних ID показується приватно з
кнопками підтвердження/скасування на 60 секунд. Авторові й боту потрібні
актуальні Manage Messages, View Channel і Read Message History у каналі.

Видалення незворотне. Запит виконується тільки після прийнятого підтвердження
автора, прив'язаного до сервера й каналу; права та збережені ID перевіряються
повторно. Нова ручна команда після невідомого результату може вибрати старіші
повідомлення, тому не повторюйте очищення навмання.

`/clear-status` читає власний 32-символьний receipt у початковому каналі,
зокрема після restart; видалення не запускає й поточного Manage Messages для
читання власного receipt не вимагає. Старий кнопковий View не відновлюється.
Clear receipts зберігаються окремими `clear_` jobs, а не справами `v2_cases`;
вони не відображаються через `/modhistory` і не виконуються reminder worker.

[Повні межі, стани й діагностика очищення](CLEAR_UA.md).

## Стани, повтори та ручна перевірка

Перед запитом зміни Discord справа `pending` атомарно записується й commit завершується.
DB-транзакція не утримується під час REST-запитів. ID — 32 hex-символи,
визначені `guild_id` та ID interaction; нової схеми БД ця функція не потребує.
Повторна доставка того самого interaction не надсилає другу дію, навіть
після перезапуску. Claim звіряє сервер, ціль, автора, дію й причину: повтор
того самого ID з іншим payload або заміною kick/ban/unban не перезаписує справу.
Нова ручна slash-команда має інший interaction ID і є новим запитом: це не спосіб безпечно повторити непідтверджену дію.

- Відмова перевірки до запиту зміни не надсилає дію. Після нового claim бот
  намагається записати `failed`; помилка запису повідомляється окремо.
  Повторний claim не змінює вже зафіксований результат попереднього запиту.
- Після помилки API, timeout або cancellation результат може залишитися
  `pending`. Навіть 404 не доводить відсутність попередньої успішної спроби:
  discord.py має власні транспортні повтори. Додаткового прикладного retry немає.
- Якщо Discord підтвердив kick/ban/unban, але фіналізація БД не підтверджена,
  відповідь прямо розрізняє ці результати. Повторювати дію для «виправлення
  запису» не можна.
- `pending` не означає, що запит зміни точно надсилали. Наприклад, процес міг
  завершитися після commit справи, але до запиту. Автоматичного визначення
  результату, повтору або ручної зміни стану через ці команди немає.

Для непідтвердженої справи відкрийте `/modhistory state:Непідтверджено`, звірте
час, автора, ціль та `case=` у Discord Audit Log. Самої відсутності учасника
недостатньо: він міг вийти самостійно. Присутність також не доводить невдачу:
людина могла повторно приєднатися. За недостатніх доказів залишайте результат
непідтвердженим. Наявність або відсутність блокування також не визначає автора
зміни. Exactly-once виконання Discord API не обіцяється: SDK може мати власні
транспортні повтори. Перевірка ролей/блокування та зміна Discord не є атомарними.

## Межі цієї ітерації

Спільний lifecycle стосується `/kick`, `/ban` і `/unban`. Старі `/warn`,
`/timeout`, `/untimeout` досі використовують попередні перевірки кешу й обробку HTTP-помилок; їхні
історичні стани не мають автоматично такої самої гарантії. Перенесення цих
команд на спільний сервіс — окрема наступна задача.

Код member moderation розділено на use-case `moderation.py`, Discord adapter
`discord_moderation.py` та guild-scoped SQL-операції `db.py`. Clear має окремі
plan/repository/service/adapter/UI межі, використовує наявну `v2_jobs` і не
змінює schema2. Повний event audit й автоматичне reconciliation ще не завершені.
Точні локальні, CI, Windows та live результати наведені в
[CORE_V2_STATUS_UA.md](CORE_V2_STATUS_UA.md); цей документ не підтверджує живий
Discord, ручний Windows-сценарій чи виробничу роботу 24/7.

Причини в історії екрануються й за потреби скорочуються з позначкою «…»,
щоб емодзі та Markdown укладалися в ліміти полів Discord; повний текст
залишається в БД. Історія не є автоматичним висновком про старі timeout/untimeout
зі станом failed: цей стан у попередньому коді міг з’явитися після неоднозначної
HTTP-помилки. Для `/kick`, `/ban` і `/unban` новий `failed` записується лише
до надсилання запиту зміни Discord.
