# Музичні джерела: перевірка 31.10.2026

Цей звіт відокремлює підтримку в коді від реального відтворення на Discord-сервері.
Під час перевірки бот не входив у Discord і не використовував токен власника.

| Джерело | Реалізований шлях | Результат перевірки |
|---|---|---|
| YouTube | HTTPS-посилання або пошук за назвою → yt-dlp → дозволений аудіопотік → FFmpeg | Перевірки коду й ізольовані тести пройшли; зовнішній пробний запит не завершився за 15 с |
| YouTube Music | `https://music.youtube.com/watch?v=...` через той самий плеєр | Посилання приймаються; зовнішній пробний запит також завершився тайм-аутом 15 с |
| Spotify | Один трек → Spotify Web API (назва/виконавець) → пошук відповідника на YouTube | Перевірено тестами з підміненим HTTP; живий Spotify API не перевірявся |
| Автоплейлист | UTF-8 файл із джерелами → та сама черга й resolver | Перевірено завантаження, пріоритет замовлень, повернення автоплею та обробку невдалих джерел |

Тайм-аут у середовищі перевірки **не доводить**, що YouTube недоступний на вашому ПК,
і не підтверджує успішне відтворення. У звичайному плеєрі ліміт resolver — 35 с;
для двох ручних проб використано коротший ліміт 15 с. Захист мережі не обходився.

## Що виправлено й уточнено

- Підтримано локалізовані посилання Spotify на один трек, наприклад
  `https://open.spotify.com/intl-uk/track/<ID>`. Плейлисти, альбоми,
  сторонні хости, credentials у URL та довільні додаткові сегменти відхиляються.
- Додано назву **`config/autoplaylist.txt`**. Якщо цей файл існує, читається саме він.
  Інакше використовується сумісний із попередньою версією **`config/_autoplaylist.txt`**.
  Файли не об'єднуються. Порожній `autoplaylist.txt` означає порожній список,
  а пошкоджений файл дає помилку замість несподіваного запуску стандартної музики.
- Опис `/music play` тепер явно згадує YouTube Music і Spotify.

Spotify тут **не джерело аудіопотоку Spotify**: потрібні власні
`Spotify_ClientID` і `Spotify_ClientSecret` у секції `[Credentials]`
файлу `config/options.ini`. Відповідник на YouTube може відрізнятися від
оригінального запису. Альбоми та Spotify-плейлисти не імпортуються.
Short/share-посилання, що потребують переходу на інший домен, не підтримуються;
використовуйте повне `open.spotify.com/.../track/...`.

## Як увімкнути та перевірити на своєму сервері

1. У `YEBOYBot.cmd` відкрийте **[25]**. Виберіть
   **[1]** для автоматичної підготовки FFmpeg/Deno, `options.ini` й увімкнення музики. Синхронізуйте команди
   через **[11]** і перезапустіть бот через **[2]**.
2. Приєднайтеся до звичайного голосового каналу. Вам і боту потрібні
   `View Channel`, `Connect`, `Speak`. Перевірте, що гучність сесії не нульова.
3. Замовте **один доступний звичайний трек**, а не live-трансляцію:
   `/music play query:<YouTube URL>`. Через `/music queue` перевірте стан,
   а фактичний звук — прослуховуванням у Discord.
4. Повторіть із посиланням `music.youtube.com/watch?...`.
5. Після налаштування власних Spotify API credentials повторіть з посиланням
   на один Spotify-трек. Якщо API недоступний, замовте пісню за назвою.
6. Для автоплею створіть `config/autoplaylist.txt`: один трек або пошуковий
   запит на рядок, коментарі починаються з `#` чи `;`. Збережіть як UTF-8.
   Приклад:

   ```text
   # Мій автоплейлист
   https://www.youtube.com/watch?v=<ID>
   https://music.youtube.com/watch?v=<ID>
   Виконавець назва пісні
   ```

   Замініть `<ID>` на реальні ідентифікатори. Перезапустіть бот після зміни файлу:
   список читається при створенні музичного модуля. Використайте `/music join`
   та `/music autoplay enabled:true` (потрібен `Manage Guild`).
7. Перевірте `/music queue`: замовлення учасника має пріоритет над автоматичним
   треком; після завершення черги автоплей продовжується. `AutoPause` може
   ставити плеєр на паузу, коли немає слухачів; це очікувана поведінка.

Ліміти автоплейлиста: до 2 МБ, до 10 000 непорожніх рядків, до 500 символів
на запис. Дублікати прибираються лише в пам'яті; файл і невдалі записи не видаляються.
Тривалість треку — до 4 годин; live-потоки не підтримуються.

## Обробка помилок зупинки голосового адаптера

Вихід із музичного worker не повинен приховувати його завершений стан: після
збою зупинки нові замовлення відхиляються до `/music stop` і нового
підключення. Навіть коли `VoiceClient.stop()` кидає виняток, очищення
належного процесу FFmpeg планується незалежно; непідтверджене завершення
не вважається успішним. Діагностика не публікує текст винятку або URL аудіопотоку.

Ці сценарії перевіряються ізольованими тестами на помилках voice-адаптера.
Вони не підтверджують довготривале відтворення реального аудіо в Discord.

## Діагностика завершеного worker

Звіт `/modules` окремо виявляє завершений музичний worker і більше
не називає сам факт голосового з'єднання готовністю плеєра.
Повідомлення рекомендує `/music stop` із повторним підключенням.
Поки Session ще не має worker, `/music queue` та `/modules` показують
статус ініціалізації без читання неіснуючої задачі.
