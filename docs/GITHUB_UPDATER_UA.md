# YEBOYBot — оновлення з GitHub через [6]

Актуально для гілки `improvement/probot-readiness` після 08.11.2026.
Головний файл залишається **`YEBOYBot.cmd`**, який запускає Windows
PowerShell і Python. EXE не потрібен. У верхній частині меню
показуються стан бота та поточна гілка з коротким SHA коміту
(якщо її можна визначити локально без мережевих запитів).

## Використання

1. Розпакуйте **весь** архів бота або встановіть його через `git clone`.
   Для першого використання оновлювача у папці мають бути актуальні
   `YEBOYBot.cmd`, `tools/windows_setup.ps1`,
   `tools/update_worker.py`, `tools/launcher/github_update.py`.
2. Запустіть подвійним кліком `YEBOYBot.cmd`. Перевірте інсталяцію
   Python 3.12 x64, .venv-v2, FFmpeg і Deno (початкова панель, а
   надалі **[19]**).
3. У головному меню оберіть **[6] Оновити YEBOYBot із GitHub**.
4. Перегляньте актуальні гілки репозиторію
   `VolshebniKGG/YEBOYBot`. Виберіть номер; у багатосторінковому
   списку `N` і `P` перемикають сторінки, `0` виходить.
   Поруч показується короткий SHA обраного коміту.
5. Ще до зупинки працюючого бота меню перевіряє через GitHub
   наявність файлів сучасного Core V2, відсутність symlink і
   сумісність Windows-імен. Це попередня перевірка; повний
   аналіз коду здійснюється після завантаження архіву.
   Прочитайте назву гілки, повний SHA і режим роботи.
   Підтвердьте **`ОНОВИТИ`** великими літерами; будь-що інше
   скасовує операцію **без зупинки бота**.
6. Якщо бот працював, контролер безпечним способом зупинить його.
   Після виходу старого Python-меню зовнішній інструмент перевірить
   джерело, зарезервує SQLite, замінить код, оновить залежності,
   перевірить конфігурацію та спробує повернути бота у попередній
   стан запуску. У тому самому CMD знову відкриється головне меню.

**Змінювати гілку вручну в інтернет-браузері або розпаковувати новий
архів поверх старих файлів більше не потрібно**, якщо поточна версія
вже містить цей updater.

## Який режим використовується

- **Git:** якщо у папці є справжній каталог `.git`; перевіряється
  офіційний HTTPS-`origin`, чистий стан робочих файлів, отримується
  вибраний SHA. Можна обрати іншу сумісну гілку: вона встановлюється
  як *detached HEAD*, без примусового переписування локальної гілки.
  `git reset --hard` і force checkout не використовуються.
- **ZIP:** якщо `.git` відсутній; Git інсталювати не треба.
  Завантажується GitHub ZIP для конкретного SHA. Шляхи, обсяги,
  дублікатні записи, Windows-імена й типи файлів перевіряються.
  Git-гілки із symlink або субмодулями не встановлюються.
  Історичні
  `data/` і `logs/` з репозиторію не встановлюються.
  Після успіху створюється локальний маніфест SHA-256 для
  контролю наступних оновлень. Наступне оновлення не
  перезапише вручну змінений раніше керований файл.

## Що зберігається

Не замінюються секрети `.env`, `.env.v2`, персональні
`config/options.ini`, `config/permissions.ini`, плейлисти,
`config/aliases.json`, `data/`, `backups/`, `logs/`,
`bin/` (завантажені FFmpeg/Deno), `.venv-v2/`, `.venv-legacy/`,
`media/` та папки локальних користувацьких файлів.
Дані SQLite перед змінами резервуються в `backups/update-*.db`.
У ZIP-режимі попередні замінені файли зберігаються в
`backups/code-update-*/` для відновлення.
Ні бот, ні інсталятор не видаляють ваші секрети або базу даних.

Після оновлення окремий Windows-процес перевіряє бібліотеки, FFmpeg,
Deno, локальну конфігурацію та схему БД без Discord login.
Якщо перевірка не пройдена, він намагається відновити попередній
код і бібліотеки. Важливо: rollback не скасовує зовнішні побічні
ефекти майбутніх міграцій БД; автоматична міграція при оновленні
коду **не виконується**. Для SQLite скористайтеся **[16]**,
для PostgreSQL — **[18]** після окремого backup.

## Обмеження та відновлення після збоїв

- Гілки, які не містять повного комплекту Core V2, сучасного
  Windows-updater та механізму recovery (зокрема старі ревізії `main`),
  **не застосовуються**. Вимоги перевіряються у вибраному
  ZIP/Git-коміті **до заміни будь-якого програмного файла**.
  Перелік гілок ≠ гарантія їх сумісності.
- Автоматичний [6] наразі розрахований на **файлову SQLite**.
  Для PostgreSQL автоматичний сценарій заблокований: спершу
  потрібна контрольована процедура PostgreSQL у **[18]**.
- У ZIP-режимі старі файли, не описані попереднім маніфестом,
  залишаються на місці. Це дозволяє не знищити власні файли.
  При першому оновленні з давнього ZIP неможливо відрізнити
  ручну правку початкового коду від архівної версії; тому
  старі програмні файли зберігаються в code-update backup.
- Не змінюйте файли й не запускайте другу копію бота під час оновлення.
  Логи перевірки: `data/v2/update-report.json`; файл плану й
  транзакції лежить у `data/v2`.
- При раптовому закритті Windows живий процес може не встигнути
  завершити rollback. Не видаляйте `update-transaction.json`,
  резервні копії чи `updater-worker-*.py`. Спочатку відновіть
  транзакцію або попередній код, а не запускайте нову установку.
