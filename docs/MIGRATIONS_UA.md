# Версійовані міграції Core V2

Поточна схема — **2**. Реєстр `core_v2/migrations.py` містить впорядковану
ревізію `002_case_updated_at`: SQLite 1→2 додає `v2_cases.updated` та заповнює
наявні рядки їхнім `created`. Історичний час останньої зміни не відновлюється.
Нові create/finish/revoke записують фактичний `updated`.

## Застосування на Windows

1. Відкрийте `YEBOYBot.cmd`, зупиніть бот через **[3]**.
2. Виберіть **[21]**. План читається без DDL й резервування.
3. Перевірте версії й ревізію. Для дозволу введіть `МІГРУВАТИ`.
4. Лаунчер бере OS lock бота й maintenance lock, перевіряє той самий файл,
   починає `BEGIN IMMEDIATE`, створює SQLite Backup API-копію v1 та перевіряє
   її integrity/schema/SHA-256. Звіт `backed_up` записується до DDL.
5. Додається колонка, зберігаються всі наявні таблиці даних та індекси,
   оновлюється marker до 2, перевіряється integrity/schema та виконується commit.
6. **[4] → [1]**. Автоматичного запуску після міграції немає.

Працюючий бот, недоступний backup, невідомий marker, неповна схема, stale plan
або зміна конфігурації/файла блокують зміну даних. Не використовуйте ту саму БД
іншими копіями проєкту й не змінюйте файл під час обслуговування.

Версія v2 при повторному [21] дає no-op. Скасування не створює копію й не змінює
схему. Нова порожня БД створюється v2 звичайним запуском; мігратор її не створює.
Запуск v1 блокується до Discord login і не повторюється через recovery loop.

## Збій і відновлення

`data/v2/migration-report.json` містить from/to, revision IDs, відносний шлях
копії, status та тип помилки. Токен, URL БД й raw exception text не включаються.
Звіт атомарно замінює попередній; повного архівного журналу всіх запусків немає.

Помилка до commit відкочує DDL/дані/marker, резервна копія залишається доступною.
За проблеми commit/диска тримайте бот зупиненим і перевірте фактичну схему [4]/[21].
Помилка звіту після успішного commit позначається окремо: БД уже оновлена,
повторювати перехід без перевірки не потрібно.

За необхідності повернення до v1 спершу використовуйте **цей новий лаунчер**:
[3] → [20] перевірка копій → [8] вибір pre-migration v1 → `ВІДНОВИТИ`.
Перед заміною буде збережено страховий snapshot поточної v2. Відновлення старої
копії замінює новіші дані; перевірте вибір та потребу зберегти страховий snapshot.
Після restore v1 потрібні сумісний код v1 або повторна міграція [21].
Старий код не читає v2; код/БД автоматично не понижуються.

Формат маніфестів лишився 1, поле schema_version тепер фактично 1 або 2.
Маніфест із невідповідною реальною версією відхиляється навіть при правильному SHA.
Копії не шифруються, містять користувацькі дані й мають зберігатися приватно.

## PostgreSQL

Нова PostgreSQL БД створюється зі схемою2. Наявна v1 під час login досі
відхиляється через MigrationRequired без DDL: автоматичної міграції немає.
Для явного upgrade стандартної public Core-схеми використовуйте **[23]**:
[1] read-only план, [2] перевірена Core-копія, [3] підтверджений1→2.
Локальний OS lock, advisory lock та SHARE table locks утримуються від перевірки
джерела через pg_dump до транзакційних DDL/data/marker і COMMIT. Налаштування,
XP, jobs, cases/pending statuses, panel rows та звичайні індекси зберігаються.

[23]→[4] використовує pg_restore тільки для окремої попередньо створеної порожньої
БД. Поточна БД не перезаписується, немає clean/drop/автоперемикання URL.
Результат COMMIT при втраті з'єднання позначається unknown_commit; перевірте
фактичну схему, не повторюйте операцію навмання. Після відновлення v1 потрібен
сумісний код або повторний upgrade на цілі. PostgreSQL code updater і перенос
SQLite→PostgreSQL залишаються окремими задачами.

Підтримуються стандартні шість Core-таблиць у public. Кастомні типи/функції,
constraints/defaults/partition/inheritance/RLS потребують окремого повного
recovery workflow й відхиляються до backup/DDL. Native client tools мають
відповідати major сервера для backup; токен/.env не копіюються, URL/password
не передаються в argv чи звіт. Копії містять приватні дані серверів, не шифруються;
SHA-256/TOC не доводять авторство. Лише довірені власні архіви.
