# PostgreSQL: резервування Core V2, міграція та recovery

Це окремий сценарій для **наявної PostgreSQL v1/v2** з підтримуваними таблицями
Core V2 у схемі `public`. Основний вхід на Windows — **YEBOYBot.cmd → [23]**.
SQLite-меню [7]/[8]/[20]/[21] не виконує PostgreSQL recovery. Перенесення даних
SQLite → PostgreSQL, автоматичне перемикання БД і PostgreSQL Git-updater у цій
ітерації не реалізовані.

## Підготовка

1. Збережіть власні налаштування й підготуйте приватне місце для копій. Для джерела
   використовується `DATABASE_URL` із змінної середовища, якщо вона задана,
   інакше з `.env.v2`. Змінна середовища має пріоритет над файлом.
2. Установіть штатні PostgreSQL **client tools** `pg_dump` і `pg_restore` з
   [офіційного джерела Windows](https://www.postgresql.org/download/windows/)
   або [офіційної інструкції Linux](https://www.postgresql.org/download/linux/).
   Обидві програми мають бути доступні через `PATH` і мати однакову major-версію.
   Для резервування потрібна **та сама major-версія, що й у сервера**: наприклад,
   сервер 17.x — обидва client tools 17.x. Системні компоненти лаунчер не
   завантажує й не встановлює. Боту не потрібні права адміністратора ОС;
   права для встановлення самих tools залежать від обраного способу встановлення.
3. Для recovery заздалегідь створіть **окрему порожню PostgreSQL БД** і підготуйте
   її URL та обліковий запис із потрібними правами створення об'єктів. Лаунчер
   не створює БД, не використовує `--clean`, не видаляє таблиці й не перезаписує
   зайняту ціль. Не запускайте бот у цій порожній БД до відновлення.
4. Зупиніть Core V2 через **[3]** головного меню та зупиніть **усі інші копії бота**,
   що використовують джерело або ціль. Вихід із головного меню [0] сам по собі
   залишає керований бот працювати.
5. Відкрийте **[23] → [1] План міграції**. Перевірте фактичну схему, ревізії
   та доступність client tools. План не створює таблиць і не мігрує дані.
   Невідома, порожня або неповна схема джерела відхиляється.

## Що входить до копії

Копія охоплює рівно шість Core-таблиць `public`: `v2_schema`, `v2_settings`,
`v2_xp`, `v2_cases`, `v2_jobs`, `v2_role_panels`, їхні дані та підтримувані індекси.
Прості додаткові btree-індекси з вбудованими operator classes/collations зберігаються. Це **не повний backup усієї PostgreSQL БД**,
сервера, ролей PostgreSQL, зовнішніх файлів, legacy JSON або `.env.v2`.

Щоб таблицева копія не пропустила нестандартні залежності, workflow відмовляє для
невідомих майбутніх Core-таблиць, додаткових Core-колонок, custom functions/types,
FK/CHECK constraints, expression/partial indexes, triggers, generated columns,
partition/inheritance, RLS/policies, нестандартних defaults, collations/operator classes/access methods та непідтримуваних видів об'єктів. Для такої інсталяції
потрібен окремий повний PostgreSQL backup/recovery план; не вимикайте перевірки.
Функції сторонніх розширень також можуть зробити БД непідтримуваною цим сценарієм.

**[23] → [2]** створює новий custom-format архів у `backups/postgres/`
з іменем `core-<UTC>-<id>.dump` і відповідний `.dump.json`.
Імена унікальні; наявні файли не перезаписуються.
Меню [4] показує дату UTC, розмір, версію схеми й SHA-256 перевірених копій.
Автоматичної політики видалення PostgreSQL-копій немає.

Перевірка включає формат `PGDMP`, маніфест, розмір, SHA-256 та native
`pg_restore --list` із точним набором Core-таблиць. Вона підтверджує цілісність
відносно маніфесту, **не автентичність**: SHA-256 не є цифровим підписом. Відновлюйте
тільки власні довірені копії. PostgreSQL archive може містити SQL-об'єкти; невідомий
файл із правильною контрольною сумою не стає безпечним для виконання.

## Явна міграція PostgreSQL v1 → v2

1. Після зупинки всіх копій відкрийте **[23] → [3] Міграція v1 → v2**.
2. Перевірте план. Для дозволу введіть точно **`МІГРУВАТИ POSTGRESQL`**.
3. Лаунчер бере локальні OS locks, PostgreSQL advisory lock і `SHARE` locks на
   Core-таблиці. Конкурентні записи блокуються, звичайне читання для `pg_dump`
   дозволене. Locks не замінюють зупинку інших ботів і не виявляють їх автоматично.
4. Повторно перевіряються джерело, версія, структура та конфігурація. Створюється
   й перевіряється native pre-migration копія **v1**; до DDL записується звіт.
5. У тій самій транзакції застосовується ревізія `002_case_updated_at`:
   додається `v2_cases.updated`, старі значення заповнюються з `created`, marker
   змінюється на 2. Час історичних змін не реконструюється. Дані справ,
   налаштувань, XP, задач і панелей зберігаються; pending справи не виконуються
   повторно й не вважаються автоматично вирішеними.
6. Після підтвердженого commit звіт має статус `applied`. Перегляньте
   **[23] → [1]**: фактична схема повинна бути v2. Лише після перевірки
   конфігурації запустіть бот через **[1] головного меню**.

Помилка до commit відкочує транзакцію; перевірена копія залишається доступною,
якщо її вдалося створити. Повторне застосування до v2 — no-op, без нової міграції
та зайвої копії. Автоматичного restart після міграції немає. Native subprocess
обмежений 180 секундами; нестача місця, відмова backup, блокування чи несумісні
tools не дають перейти до DDL.

## Recovery у нову порожню БД

1. Залиште всі копії бота зупиненими. У `.env.v2` поки зберігайте поточне джерело.
2. Відкрийте **[23] → [4] Відновити у нову порожню БД** та виберіть архів зі списку.
3. Введіть URL **окремої заздалегідь створеної порожньої цілі** у прихованому
   prompt. Лаунчер не повторює URL на екрані й не зберігає його у звіті.
   Якщо приховане введення недоступне, операція відмовляє; відкрийте
   `YEBOYBot.cmd` у звичайному CMD, не вводьте credentials у видимий fallback.
4. Для дозволу введіть точно **`ВІДНОВИТИ POSTGRESQL`**. Поточне джерело як ціль
   заборонене; непорожня ціль із таблицями, views, sequences або custom functions
   відхиляється. Цільові об'єкти не очищуються й не перезаписуються.
5. Перевірені байти архіву копіюються в приватний staging-каталог та перевіряються
   повторно. Native `pg_restore` працює з `--single-transaction --exit-on-error`;
   після нього перевіряється фактична версія відновленої схеми.
6. За статусу `restored` перевірте дані в новій БД. Джерело залишилось незмінним.
   Для переходу вручну змініть `DATABASE_URL` у фактичному джерелі конфігурації
   (врахуйте пріоритет змінної середовища над `.env.v2`). Лаунчер цього не робить.
7. Якщо відновили **v1**, перед запуском актуального Core V2 виконайте
   **[23] → [3]** вже для цієї БД. Копія v2 відновлюється як v2. Старий код не
   вмикається автоматично; downgrade схеми не виконується.

Цільовий сервер не може бути старішим за major-версію tools, що створили архів.
Пара client tools повинна мати однакову major-версію й не бути старішою за ціль
та формат копії. Сценарій із тим самим PostgreSQL 17 перевірено локально;
успіх довільного переходу між major-версіями не заявляється.

## Credentials, TLS і приватність

Для native tools host/port/database/user/password передаються через тимчасове
середовище дочірнього процесу, а не через аргументи чи URL у command line.
Успадковані `PG*` параметри не можуть непомітно змінити підключення. Сирі stderr
libpq, parser exceptions і credentials не виводяться та не додаються до JSON-звіту.
Середовище процесу не є сховищем секретів від інших процесів того самого
користувача або адміністратора ОС.

Підтримується TCP URL драйвера `postgresql+asyncpg` з необов'язковим `ssl=<mode>`;
приймаються `disable`, `allow`, `prefer`, `require`, `verify-ca`, `verify-full`.
Це перелік допустимих параметрів, не рекомендація вимикати TLS. Виробничий
TLS/mTLS у цій ітерації не перевірений. Успадковані `PGSSL*` та окремі URL
certificate-параметри відхиляються, щоб native tools і asyncpg не отримали різні
TLS-політики. Підтримка узгоджених custom CA/SSLContext потребує окремої роботи;
не обходьте відмову зниженням вимог перевірки сертифіката.

Архіви містять приватні дані серверів, зокрема причини модерації й тексти задач,
і **не шифруються**. Файли `.env.v2` та credentials процесу не додаються до архіву;
назви власників об'єктів можуть залишатися в metadata архіву. Файли створюються
з режимом 0600, каталог — 0700 на POSIX; Windows ACL не перевірені цими mode bits.
На Windows окремо обмежте доступ до каталогу засобами ОС. Не публікуйте копії,
маніфести або діагностичні дані з приватним вмістом. `--no-owner --no-acl` означає,
що права й власники PostgreSQL не відновлюються з цього Core-архіву.

## Звіт і неоднозначний результат

`data/v2/postgres-report.json` атомарно замінюється останнім звітом, не є повною
історією всіх операцій. Основні статуси операцій наведено нижче; no-op `unchanged`
повертається без перезапису файла звіту.

| Статус | Значення та дія |
|---|---|
| `unchanged` | Джерело вже v2, нова міграція не потрібна |
| `backed_up` | Створено перевірену копію; це саме по собі не підтверджує commit міграції |
| `applied` | Commit міграції підтверджений, звіт записаний |
| `failed` | Операцію до спроби commit не підтверджено; перевірте схему й наявну копію, залиште бот зупиненим |
| `unknown_commit` | Commit уже міг відбутися, але підтвердження втрачено; спочатку перевірте фактичну схему, не повторюйте дію навмання |
| `restored` | Native restore завершився й фактична відновлена версія підтверджена |
| `restored_unverified` | Restore завершився, але наступна перевірка/звіт не підтвердились; збережіть ціль і перевірте її |
| `restore_failed` | Recovery не підтверджено; це не доводить, що ціль порожня після мережевого збою |

Якщо звіт не вдалося записати після commit, він може зберігати старіший статус.
Повідомлення меню прямо вимагає перевірити фактичну БД. Не видаляйте джерело,
ціль або страховий архів, не робіть автоматичний повтор чи «відкат» через
неоднозначний мережевий результат.

## Фактичні перевірки та межі

Локально виконано 76 нових цільових тестів, включно зі справжнім PostgreSQL
17.11 та native `pg_dump → upgrade → pg_restore` у одноразових БД. Перевірено
збереження payload двох guild, простого custom index і pending cases/jobs,
backfill timestamp, rollback, повторне застосування, відмову непорожньої цілі
та приховування connection credentials. Це не виконання операцій над БД власника.

Повні актуальні totals, SHA й CI результати — у [CORE_V2_STATUS_UA.md](CORE_V2_STATUS_UA.md).
Native PostgreSQL workflow на Windows, виробничий TLS, live Discord і 24/7
ще не підтверджені. Наявність recovery-копії не вирішує pending moderation cases,
не гарантує exactly-once Discord send і не робить бот виробничо готовим.

Під час Ctrl+C обмежений за часом native worker спочатку завершується, щоб
не звільняти source locks посеред pg_dump. Потім міграція скасовується; звіт
може мати cancelled/unknown_commit. Після переривання recovery стан restore_unknown
означає, що ціль треба перевірити. Примусове завершення процесу/ОС не дає
гарантії запису звіту: не повторюйте операцію до перевірки фактичної схеми.
