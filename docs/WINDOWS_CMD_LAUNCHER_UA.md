## Автозапуск Windows через [15]

Це необов'язковий запуск після входу поточного користувача Windows. Завдання
не створюється під час встановлення чи звичайного запуску бота. До входу
користувача бот таким способом не запускається; це не служба Windows.

1. Установіть середовище через `YEBOYBot.cmd`, налаштуйте Discord через **[11]**
   або **[12]** і перевірте звичайний запуск.
2. Відкрийте **[15]**, виберіть **[1]** та введіть `УВІМКНУТИ АВТОЗАПУСК`.
3. Після успішного підтвердження завдання наступний вхід користувача запустить
   бот у фоновому режимі. Для запуску зараз скористайтеся **[1]** головного меню.
4. Щоб вимкнути, відкрийте **[15] → [2]** і введіть `ВИМКНУТИ АВТОЗАПУСК`.
   Підменю видаляє тільки перевірене завдання цієї копії. **[0]** повертає назад.

Перед увімкненням перевіряються `.venv-v2/Scripts/python.exe`, `pythonw.exe`,
локальна конфігурація через doctor і критичні імпорти. Ця перевірка не входить
у Discord і не підтверджує чинність токена. Помилка конфігурації або імпортів
блокує зміну завдання — скористайтеся **[4]**, **[5]** та журналом **[9]**.

Завдання працює з правами поточного користувача без підвищення привілеїв
і збереження пароля. Воно викликає `pythonw.exe -m core_v2.managed` з робочою
папкою проєкту, тому додаткове CMD-вікно не відкривається. Саме завдання
не приховане: його можна знайти у Планувальнику за ім'ям `YEBOYBot-CoreV2-…`.
Належність визначається для конкретної папки та SID користувача; перед змінами
перевіряються також дія, користувач, робоча папка й інші очікувані параметри XML.
Чуже або змінене завдання не перезаписується й не видаляється через меню.

Статуси **[15]** описують лише налаштування Планувальника:

- «Увімкнено» — відповідне перевірене завдання увімкнене.
- «Вимкнено» — перевірене завдання існує, але вимкнене у Планувальнику.
- «Завдання видалено» — команда вимкнення успішно видалила власне завдання.
- «Невідомо» — запит не підтвердив стан. Відсутність завдання, відмова доступу
  або недоступний Планувальник можуть дати однакову відповідь; після видалення
  повторне відкриття меню також може показувати «Невідомо».
- «Чуже або змінене завдання» — перевірка належності не пройдена.

Готовність Discord перевіряйте за станом бота та журналом, а не за станом
автозапуску. Вимкнення автозапуску не зупиняє вже запущений процес — для цього
використовуйте **[3]** головного меню. Повторний запуск цієї копії обмежують
політика завдання та OS lock бота.

Планувальник не налаштовано повторювати запуск після аварії процесу:
`RestartOnFailure` не додається. Обмежені повтори після Python exceptions
залишаються відповідальністю managed runtime; kill/segfault/збій ОС потребують
ручного запуску або наступного входу користувача. Після перенесення папки чи
видалення venv старе завдання не переналаштовується автоматично. Перед
перенесенням вимкніть автозапуск у старій папці; після встановлення в новій
папці увімкніть його повторно.

На Linux цей пункт показує недоступність. Автоматизовані тести не реєструють
реальних завдань ОС; створення, запуск після входу та видалення завдання на
Windows 10/11 потребують окремої ручної перевірки.

## Резервування та відновлення

**[7]** створює перевірену копію через SQLite Backup API в `backups/v2-*.db`.
Це окремий знімок без залежності від WAL/SHM робочої БД. Оригінальна БД може
працювати під час створення копії. Поруч записується маніфест `.db.json`:
версія формату, SQLite, версія схеми, дата UTC, розмір у байтах і повна SHA-256.
Маніфест не містить токена, URL БД, шляхів джерела або конфігурації.

**[20]** показує звичайні й архівні копії з датою, розміром, SHA-256 та станом:

- «Перевірено» (`verified`) — розмір і SHA-256 збігаються, цілісність SQLite та схема перевірені.
- «Стара копія без SHA-256» (`legacy`) — маніфест відсутній; SQLite і схема перевірені, початкова SHA-256
  та дата невідомі.
- «Перевірку не пройдено» (`invalid`) — файл, маніфест, цілісність або схема не пройшли перевірку.

Перевірка читає повний файл, тому великі копії можуть оброблятися довше.
**[10]** окремо перевіряє `integrity_check`, підтримувану схему v1/v2 та потрібні таблиці/колонки
поточної БД без міграцій.

Для **[8]** спочатку зупиніть бот через **[3]**, виберіть номер копії й введіть
`ВІДНОВИТИ`. Перед зміною поточної БД перевіряються розмір, SHA-256, цілісність
та схема фактичних байтів підготовленого знімка. Відновлення утримує той самий
OS lock, що й бот, і спільний lock резервування до завершення. Перед заміною
створюється перевірена копія поточних даних; якщо вона не створилася, відновлення
не починається. Якщо поточна БД відсутня, новий файл створюється з вибраної копії.

Для `legacy` додатково введіть `СТАРА КОПІЯ` перед основним підтвердженням.
Це не скасовує перевірку SQLite та схеми. Неправильний маніфест чи невідповідність
SHA-256 блокують відновлення; вважати таку копію старою автоматично не можна.
Символьні посилання замість копії/маніфесту не підтримуються; відновлення копії
поверх того самого файла, включно з hardlink, відхиляється. Невідома схема
відхиляється: автоматичного downgrade немає.

Після відновлення запустіть **[10]**, потім **[1]** і перевірте `/status` та дані.
Пошкоджену поточну БД спершу збережіть окремо: неможливість її резервування блокує
автоматичне відновлення. Блокування захищає процеси цього каталогу; не відкривайте
ту саму БД іншими копіями бота.

### Політика зберігання через [20]

1. Перегляньте каталог. Enter завершує дію без змін.
2. Введіть кількість останніх перевірених копій, які потрібно залишити поза
   архівом: від 1 до 10000.
3. Перевірте показаний список старіших копій.
4. Введіть `АРХІВУВАТИ`, щоб перенести вибрані пари `.db` + `.db.json`
   у `backups/archive/<uuid>/`. Інше введення скасовує дію.

Поточна БД, останні N перевірених копій, `legacy`, `invalid` і вже архівні копії
не включаються до плану. Перед перенесенням план і перевірки виконуються повторно;
якщо вибрані файли більше не дозволені, потрібно повторити перегляд.
Архівні копії залишаються у каталозі та доступні через **[8]**.
Перенесення виконується для кожної пари окремо: якщо пізніша копія спричинила
помилку, попередні вже можуть бути в архіві; вони залишаються доступними для відновлення.

Архівування не запускається під час створення копії чи оновлення, не видаляє
файли назавжди й не звільняє дисковий простір. Кількість N задається для поточної
операції, а не як фоновий розклад. Якщо операція перерветься через збій ОС,
збережіть усі файли в `backups/` і `backups/archive/`, перевірте каталог через
**[20]** та не видаляйте неповні пари до ручної перевірки.

Копії не шифруються й можуть містити повідомлення та інші дані серверів.
Конфігурація й токен із `.env.v2` не додаються, але користувацький вміст БД
не фільтрується. Зберігайте копії приватно й переносіть разом `.db` та `.db.json`.
SHA-256 перевіряє цілісність відносно маніфесту, не авторство: навмисна заміна
обох файлів не захищена цифровим підписом.

PostgreSQL backup/restore й архівування через це SQLite-меню не підтримуються;
для PostgreSQL є окремий перевірений native workflow [23], див. POSTGRES_RECOVERY_UA.md.
Ручний сценарій на Windows 10/11 і відновлення з живим Discord залишаються
неперевіреними; результати автоматичних перевірок публікуються окремо для коміту.

## Локальна діагностика та JSON-звіт — 25.10.2026

[4] перевіряє Python 3.12, установлені пакети та критичні імпорти, конфігурацію
і файлову SQLite. БД відкривається mode=ro: quick_check, версія v1 та потрібні
колонки; перевірка SQL має progress deadline 2 секунди й lock timeout 1 секунду.
Це не повний integrity_check, тест запису або міграція. Відсутня БД не створюється;
вона готується штатним запуском [1]. PostgreSQL отримує unknown, без підключення.
[18] додатково атомарно зберігає data/v2/diagnostics/latest.json, замінюючи попередній
звіт. Токен, URL БД, ID серверів, nonce, шляхи, журнали й тексти винятків
не включаються. Каталог data/ виключено з Git.
Runtime readiness вимагає свіжого heartbeat і стану «Готовий»; прострочений heartbeat
не підтверджує Discord ready. Чинність токена, мережа та Discord API не перевіряються.
Статуси JSON: ok/error/unknown; local_checks_passed=false також для unknown.
За невдалої локальної перевірки CLI повертає 1, але [18] зберігає доступний звіт.
Кожен виклик меню запускає новий Python-процес, тому перевірка читає актуальну .env.v2.
Локально пройшли 3 stdlib тести експорту/збереження попереднього звіту та відсутньої БД;
інші тести перевіряються в CI нового коміту через недоступні локальні залежності.

## P0: контроль процесу та перевірка схеми

Помилка запису heartbeat тепер завершує керований клієнт і обидві його задачі,
записується у журнал та повертає код 1. Автоматичні повтори для ControlFailure
вимкнені: без записуваного стану новий клієнт не запускається. Запит штатної
зупинки перевіряється перед heartbeat; звичайні мережеві retry залишаються
обмеженими, попередній клієнт закривається до нового запуску.

Якщо запуск завершився з такою помилкою: перегляньте [9], перевірте вільне місце,
права запису в data/v2 і тип об'єктів managed.json/managed.tmp. Після усунення
причини виконайте [4], потім [1]. База даних цим виправленням не видаляється.
Зовнішнього супервізора kill/segfault/збоїв ОС ще немає.

Перед WAL/створенням таблиць перевіряється сумісність наявної схеми. Невідома
версія, порожній/неправильний v2_schema, наявні v2-дані без маркера або неповна
v1 схема відхиляються без автоматичного ремонту. Початкове створення SQLite
виконується транзакційно; помилка DDL відкочує всі його таблиці. Налаштування
та XP підтримуваної v1 зберігаються при повторному запуску.

Не редагуйте version вручну для обходу відмови. Використайте сумісний код і
збережіть оригінал перед перевіреним відновленням. Повний ланцюжок версійованих
міграцій залишається окремим наступним етапом; автоматичного downgrade немає.
Ручний Windows 10/11 і живий Discord API цими тестами не підтверджуються.

## Міграції через [21]

[21] читає фактичну версію без змін. Для SQLite v1 показує ревізію
`002_case_updated_at` і після `МІГРУВАТИ` бере bot/backup locks, створює та
перевіряє копію вихідної БД, виконує транзакційний перехід 1→2 і зберігає
`data/v2/migration-report.json`. Працюючий бот блокує міграцію — спершу [3].
Налаштування, XP, нагадування й справи зберігаються. Нова колонка справи
`updated` спочатку дорівнює `created`; це не реконструкція історичного часу.
Нові create/finish/revoke надалі записують фактичний час зміни.

Зміна конфігурації або заміна файла після плану блокує застосування; backup
прив'язаний до перевіреного джерела. Помилка до commit відкочує транзакцію;
копія зберігається. Якщо commit пройшов, але звіт не записано, меню прямо
повідомляє про оновлену БД. Перевірте [4]/[21] перед повтором.

Повторне застосування v2 — без змін і нових копій. Скасування підтвердження
не виконує DDL. Автоматичного downgrade немає. Відновлення v1 через [8]
можливе лише явно: страховою копією стане поточна v2, а для запуску потрібні
сумісний старий код або нова міграція через [21]. Старий код v1 не читає v2.
Цей пункт підтримує SQLite; PostgreSQL upgrade доступний через [23] з native backup
workflow. [Повна інструкція](MIGRATIONS_UA.md).
